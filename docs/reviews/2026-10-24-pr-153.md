## Findings

### R1 — Explicit category reset

- Feedback: https://github.com/narumiruna/otter/pull/153#discussion_r4355699454.
- Evidence: `ExpenseEditorState.input` converts an empty category to `nil`. `NewExpense` then omits it. `TripClient.updateExpense` sends that body as PATCH. `server-expenses.ts` checks `"category" in body`; absence keeps the old category. Its `expenseCategoryFromBody` accepts an empty string and maps it to `其他`.
- Scope: the new native expense editor cannot save a category reset. This breaks its expense-editing goal.
- Severity: P2. The save succeeds but leaves the wrong category.
- Outcome: Already addressed. Edit resets now send an explicit empty category. New and queued drafts keep the existing default contract.
- Fix and validation: send an empty string for an edit reset. Keep omitted categories for new and queued drafts. Check the encoded PATCH body and unchanged draft behavior.

### R2 — Equal-split remainder order

- Feedback: https://github.com/narumiruna/otter/pull/153#discussion_r4355699463.
- Evidence: `ExpenseEditorState.toggle` appends a selected ID. Its preview uses that order. `participantSharesFromBody` returns no stored shares for equal splits. Both `packages/core/src/settlement.ts` and native `Finance.accounts` use the group participant order for the saved calculation. The existing description-only edit test expects the wrong preview order. The editor footer also states the wrong rule.
- Scope: the new native preview can show different amounts from the saved accounts.
- Severity: P2. The remainder can appear under the wrong participant.
- Outcome: Already addressed. Equal previews use group participant order. Input order and explicit shares are unchanged. The footer is corrected in all 18 languages.
- Fix and validation: use group participant order only for equal previews. Keep input order and explicit shares unchanged. Test reselection, description-only edits, and preview agreement with account calculations. Correct the footer in all supported languages.

### R3 — Completed group updates after a tab change

- Feedback: https://github.com/narumiruna/otter/pull/153#discussion_r4355699470.
- Evidence: `PeopleView` and `GroupSettingsView` invalidate page state on disappearance. `GroupManagementState.run` rejects a successful response if that page generation changed. Its sole acceptance callback also updates the workspace. `TripDetailView` does not reload on tab changes. A committed representative or settings update can therefore leave old balances and permissions visible.
- Scope: the new native management screens discard valid workspace data.
- Severity: P2. The workspace remains stale until a later reload.
- Outcome: Already addressed. Successful results publish for the same session. Page-local callbacks still require the same page generation. Copy/delete navigation also checks the selected workspace.
- Fix and validation: separate same-session result publication from page-local acceptance. Keep page-generation guards for form state and session guards for both paths. The group list applies copy/delete navigation only if the original workspace is still selected. Test page dismissal, cancellation after a completed write, and account changes.

### R4 — Receipt loading after cancellation

- Feedback: https://github.com/narumiruna/otter/pull/153#discussion_r4358383147.
- Evidence: the delete-receipt toggle clears `selection` and replaces `requestID`. The nil-selection handler does not clear `loading`. The old task can no longer clear it because its deferred cleanup checks the old ID. `ExpenseEditorView` disables Save, Cancel, and dismissal while this flag is true.
- Scope: the new receipt picker can lock the native expense editor.
- Severity: P2. Recovery requires leaving or restarting the app.
- Outcome: Already addressed. `ReceiptRequestState` owns both the request ID and loading flag. Cancellation invalidates the ID and clears loading together. Old completions cannot clear a newer request.
- Fix and validation: invalidate the request and clear loading together. Check that an old task cannot apply a photo or clear a newer request's loading state.

### R5 — Queue edit lock after dismissal

- Feedback: https://github.com/narumiruna/otter/pull/153#discussion_r4358383156.
- Evidence: `ExpenseQueueView.edit` acquires the queue lock before awaiting the trip request. Only Close is disabled while it waits. There is no queue-dismissal guard. A late response can assign an editor to the dismissed view. `ExpenseQueue.synchronize` skips locked IDs; normal release occurs only after editor dismissal or an error/session change.
- Scope: the new queue UI can stop a saved draft from synchronizing.
- Severity: P2. The draft remains stored, but synchronization skips it until the lock is released or the app restarts.
- Outcome: Already addressed. Pending edits block interactive dismissal. Disappearance invalidates the edit request and releases its pending lock. Both suspension points reject late completion. Active editor locks remain until the editor closes.
- Fix and validation: block interactive dismissal during a pending edit, invalidate the pending request on disappearance, and release its lock after every late completion. Check synchronization after lock release and preserve locks while the editor is active.

## Additional finding

### F1 — Separate the smoke and live test instructions

- Evidence: `apps/ios/README.md` joined the live-suite text to the smoke-case sub-item without a space or a new line.
- Scope: the PR adds both native suites and their instructions. The combined line obscures their different API requirements.
- Severity: P3. This is a documentation defect, not a runtime defect.
- Outcome: Already addressed. Smoke and live test instructions use separate list items.
- Fix and validation: use separate list items. Check the Markdown source and `git diff --check`.

### F2 — Completed settlement deletion after a tab change

- Evidence: `OverviewView.delete` checks the page `revision` before it calls `onPayload`. `onDisappear` changes that revision. Its List is disabled during deletion, but the workspace tab bar is not. A successful server deletion can therefore be discarded after a tab change, as in R3.
- Scope: the PR adds this native settlement workflow. The workspace must show the committed payment state.
- Severity: P2. Balances and suggestions remain stale until a reload.
- Outcome: Already addressed. Successful payment deletion updates the same-session workspace without a page-revision check. Local error text still uses the page revision.
- Fix and validation: publish a successful deletion for the same session. Keep page-revision checks for local error text. Check the native build and settlement workflow.
